# Scripture Reading App — Playbook

*Learnings, preferences and decisions from building the Shri Ramcharitmanas reader (Oct 2026). Share this file at the start of any new scripture project (Gita, Sundarkand, Hanuman Chalisa, Bhagavat, Gurbani, etc.) so the work can start without back-and-forth.*

---

## 1. How I like to work

- **Accuracy over speed.** Wrong spelling changes meaning. Never pull text from random websites; use my own books (PDFs I upload) as the single source of truth.
- **Fix, don't annotate.** If you find discrepancies, fix them in the data directly. No "पाठभेद" tags, no "variant" markers, no accuracy/about/documentation pages inside the app.
- **No AI attribution in the product.** No "generated by Claude" notes anywhere (word popups included). Show content only.
- **Every word must have a meaning.** No "meaning not available yet" rows. If something is missing, hide it rather than show an empty placeholder.
- **Respect the publisher's style.** Example: Gita Press joins postpositions (महाराजके, रामजीका). That is correct house style. Do not "modernise" it.
- **Keep the app generic.** Don't tie it to my personal reading schedule. Schedules are served by the built-in plans (e.g. 30-day / 9-day).
- **Explain what you're changing.** When making changes, say in plain words what changed and why, not just "updated the artifact".
- **Show screenshots.** Test on a phone-size screen (390px wide) before telling me it's done.
- **Ask only when a decision is really mine.** Otherwise pick the sensible option and tell me.
- **Deliverables:** a private claude.ai artifact link (shareable) and an offline single HTML file. Update both every time.

## 2. Source material & accuracy rules

- **Source of truth:** the publisher's printed book (Gita Press for Hindu scriptures). Their verse numbering, section structure, topic names (from the book's table of contents) and meanings are authoritative.
- **Two books are common:** a Hindi edition (verse + Hindi bhāvārth) and an English edition (verse + transliteration + English translation). They are typeset differently and must be aligned with each other.
- **Cross-check everything:**
  - Extract text from the PDF's text layer and also OCR the page images (Tesseract `hin`). Compare the two. Agreement should be well above 95%. Review every disagreement by eye.
  - Validate transliteration ↔ Devanagari by converting the transliteration back to Devanagari and diffing.
- **Footnotes are content.** Keep them, attach them to the verse that carries their mark (\*, †, ‡, §, #), and fix any that continue from a previous page.
- **Corrections layer:** the app keeps the book text untouched and lets each reader save personal corrections ("Correct the text or meaning"), which can be reverted.

## 3. Content structure (how scripture should be organised)

- **Hierarchy:** Book → Part (kāṇḍa / adhyāya / skandha) → Section → Verse.
- **Ramcharitmanas sections:** chaupāīs are grouped under the dohā that *follows* them ("Dohā 2" = chaupāīs before dohā 2 + dohā 2). This is the standard citation (1.2.1). Each part opens with verses before Dohā 1 (ślokas, sorathās).
- **Pages = the book's own sections, never topics.** One page = one dohā group (or the opening verses before Dohā 1). When a topic starts mid-section, show its heading *inside* the page, just before that verse. Never split a section into separate pages because of a topic.
- **Multiple orderings of the same text:** by part (kāṇḍa), 30-day Māsapārāyaṇa and 9-day Navāhna (vishrams). Mark vishram/pause boundaries inline. Tapping a vishram must open at its **start**. "Continue where you left off" is the separate resume path.
- **Topic list:** each topic shows the exact verse where it starts (e.g. "Dohā 2 · Chaupāī 2", "Sorathā 5"), not the page range.
- **Labels for opening verses:** name them by type and number ("Śloka 1–7", "Sorathā 5"), not a vague "Invocation" that conflicts with topic names.

### Verse types (Ramcharitmanas)

| Type | Short (Hi / En) | Note |
|---|---|---|
| चौपाई Chaupāī | चौ० / Cau. | 4 quarters × 16 mātrās. Number ।।१।। at end. |
| दोहा Dohā | दो० / Do. | 13+11 mātrās per line. Closes a section. |
| सोरठा Soraṭhā | सो० / So. | 11+13, the reverse of a dohā; rhymes in the middle. |
| छंद Chhand | छं० / Cha. | Longer lyrical metres (Harigītikā etc.). |
| श्लोक Śloka | श्लो० / Śl. | Sanskrit, syllable-counted; opening invocations. |

## 4. Reader UX — my preferences

### Overall principles
- Simple, clear, intuitive. Common things visible; uncommon things behind the ⋮ menu.
- Optimise space; reading comes first. Nothing should pull attention away from the verse.
- Icons must be meaningful. No extra phone permissions.

### Verse layout
- **Verse text:** bold, centred, large. Meaning in normal weight below it.
- **Per verse:** the verse, then the Hindi meaning, then the word list, then the English meaning, then the footnotes, then my notes.
- **One meaning per verse in each language.** If the English book translates several verses as one paragraph, split it so each verse gets its own part. Never change the words; split at sentence boundaries.
- **The verse number appears in the verse** (।।१।।), in Devanagari digits in Hindi mode and Latin digits (1) in English mode.
- **Verse markers must never shift the centred text.**
  - The type label (चौ० / दो० / सो० / श्लो०) sits at a fixed spot at the **left edge of the first line**. Tapping it shows the full name and a one-line explanation.
  - **Bookmark + ⋮** sit at a fixed spot at the **right edge of the last line**.
- **No per-verse button rows.** हिं / En / शब्द toggles live in the top bar and apply to the whole book. They are the same flags as in Settings: changing one place changes the other.
- **No redundant headings.** The bottom bar already shows the section, so no extra "Chaupāīs before Dohā N" banner.

### Header and navigation
- **Top bar:**
  - Back button.
  - Two lines: the small line shows exact position ("Bāla-kāṇḍa · Dohā 2 · Chaupāī 1"), the big line shows the current topic.
  - The हिं / En / शब्द toggles.
  - ⋮ menu, holding search, recitation mode, timer, go-to, transliteration and text size.
- Both header lines update as you scroll.
- **Bottom bar:** ‹ Previous · section name ▾ (tap to jump) · Next ›. Swipe left/right also moves between pages.
- Opening a topic scrolls to its heading, fully visible below the top bar.

### Language of the interface
- One language at a time, never both side by side.
- English if English meaning is on (including when Hindi is also on); Hindi if only Hindi is on.
- This applies to every heading (part names, topic names), labels, menus and numbers.

### Word-by-word meanings
- Tap any word for its meaning in Hindi and English together, in a clean popup with content only.
- The शब्द toggle shows the full word list under each verse.

### Features that must be there
- Bookmarks, personal notes/commentary, search across verse, meaning, transliteration and English.
- Saved progress per ordering, plus a "Continue where you left off" card.
- Vishram completion tracking ("Mark vishram complete").
- Personal data in a separate personal store, with export/import as a file and multiple reader profiles.
- Recitation mode (verses only, larger text), reading timer, text size, light/dark theme, optional Roman transliteration.
- A pūjā-vidhi / āratī section when the book includes it.

## 5. Personal data & sharing

- Every reader must have their **own** notes, bookmarks, progress and settings.
- **Claude artifact link:** a signed-in viewer in my organisation syncs to their own private store across devices. Outside viewers (public link) cannot write to the cloud, so their data stays in that browser on that device; the backup is Export.
- **Offline HTML file:** data stays in that browser on that device; Export/Import for backup.
- **For the public, "forever":** a free installable web app (PWA) on GitHub Pages or Cloudflare Pages, with offline support and optional Google sign-in sync through Firebase's free tier. It could later be wrapped for the Play Store. No ads, ever.
- **Copyright:** original scripture text (e.g. Tulsidas) is public domain. Publisher translations and commentary (e.g. Gita Press Hindi bhāvārth and English translation) are copyrighted. Personal/family use is fine; public distribution needs the publisher's permission. Otherwise ship a version with only the original text and our own word meanings.

## 6. Technical learnings (pipeline)

### PDF text extraction
- **Hindi Gita Press PDFs** (often calibre-made, Noto Sans Devanagari CID font) have a **broken text layer**: missing glyphs, wrong matra order. Decode from glyph IDs (PyMuPDF `get_texttrace()`) with a hand-built glyph → Unicode map.
  - Pre-base ि variants.
  - Reph combos (र्+matra).
  - Conjuncts (ञ्ज, ड्य, ढ्य …).
  - Nukta forms.
  - Empty placeholder glyphs.
  - Zero-advance spaces: after a halant, a space means ZWNJ; between consonants it means a missing ्.
- **English Gita Press PDFs** mix fonts:
  - Devanagari in a legacy **Chanakya/Kruti-style 8-bit font**. Garbage like `‚Ê0ó’¢Œ©U°` is Devanagari; skip it or map it.
  - Bold transliteration in a custom encoding (å=ā, ∂=ī, µu=ū, ¢=ṭ, ƒ=ṇ, ›=Ś, ~ or a raised dot = chandrabindu). Write a converter and verify it.
  - Legacy-font Devanagari also leaks into footnotes (Pāṇini sūtras, technical terms). Search for those characters (Ê Á ⁄ ﬂ ¡ Ÿ Ã ∑ ◊ …) and hand-fix each occurrence.
- Use character-level extraction (rawdict) with x-positions to place diacritics correctly.
- **Footnotes run across pages.** A footnote starting with a lowercase word is a continuation; attach it to the previous one.
- **Missing spaces after full stops** ("peril.You") are common; normalise them.

### Alignment and structure
- Build verse items with stable IDs: `kand.section.typeN` (e.g. `bal.2.cau1`, `bal.7.do7ग`).
- Align Hindi and English editions by matching normalised transliteration to Devanagari words (difflib). Expect English groups to cover several verses.
- **Splitting a group translation per verse:**
  - Pre-cut sentences/clauses mechanically.
  - Let agents decide each verse's start segment by reading the verse, transliteration and Hindi meaning (no heuristics).
  - Allow mid-sentence splits ("segment:word").
  - Assert that the concatenated parts equal the original text exactly.
  - Watch out for groups whose English is printed with the next verse (empty groups); merge and split those by hand.
- Topics come from the book's table of contents. Map their start verses carefully, especially around section boundaries.

### Glossary (word-by-word)
- Collect every distinct word form (~15k for Ramcharitmanas).
- Write meanings with parallel agents in batches: Hindi gloss + English gloss, aiming for 100% coverage.
- Normalise lookups (strip punctuation, nukta and chandrabindu variants).

### App build
- A single self-contained HTML file: embedded fonts (Noto Serif Devanagari, Literata), embedded JSON data (~10 MB), no external calls.
- In the artifact: no `alert/confirm/prompt` (use in-page sheets); no `<a download>` (use the downloads capability); localStorage wrapped in try/catch.
- Personal state lives in a single object with a timestamp; cloud sync is per user (`data/users/<id>/state`).
- Test with Playwright (Chromium) at 390×844 mobile.
  - Scripted checks: no page errors, export/import, notes, toggles, topic-jump heading visibility.
  - Screenshots reviewed by eye.

## 7. Bugs we hit — check these early next time

1. Duplicate per-verse controls when one translation covers several verses. Fix: one meaning per verse.
2. Topic headings creating extra pages, causing a "Dohā 2" page that contains only chaupāī 1. Fix: pages by section only.
3. Header still showing the old topic or section label. Fix: compute it from the top visible verse.
4. Vague "Invocation" label conflicting with topic names.
5. Topic list showing page ranges instead of start verses.
6. Opening a plan segment (vishram) jumped to the saved position instead of the start. The saved position also got polluted by a neighbouring segment on the same page. Fix: open at start; remember the verse actually opened.
7. Topic heading hidden under the sticky header. Fix: `scroll-margin-top`.
8. Footnote mismatched to the wrong verse when markers restart per printed page. Fix: match notes to markers in order.
9. Inline icons pushing centred verse text off-centre. Fix: absolutely positioned side markers.
10. Long lines on phones: keep the verse number unbroken (no wrap inside ।।१।।).
11. Mixed digits: use Devanagari digits in Hindi mode and Latin digits in English mode, everywhere.

## 9. Added later — product direction and more preferences (Oct 2026)

### Product direction
- **It is a website of its own** (GitHub Pages, repository **`scriptures`**), installable on the phone. Nobody should ever be asked to upload audio or data files.
- **Library of works, any depth.** Everything the owner studies goes into one library: e.g. *Gosvāmī Tulasīdāsa › Śrī Rāmacaritamānasa* (2 levels) or *Veda › Sāmaveda › Upaniṣad › (name) › text* (4 levels). The library screen walks this tree with breadcrumbs. Every work then gets the **same experience**: natural divisions (kāṇḍa, adhyāya…), reading plans (pārāyaṇa), bookmarks, notes, progress, search, audio, sources.
- **The verse + its number is the core entity.** Hindi meaning, English meaning and audio are **attributes from selectable sources** (Settings › Sources). Today: Gita Press Hindi, Gita Press English, Pt. Kamlesh Upadhyay audio; tomorrow more. Changing a source must make the whole app (reader, search, follow-along audio) use it.
- **Word meanings (glossary/roots) are fixed** and shared — they never change with the source.
- **Data layout (website):** see `docs/LIBRARY.md`. In short: `library/index.json` (the shelf), `library/glossary/<lang>.json` (dictionaries by language), `library/<path>/work.json` (text, divisions, topics, plans, vidhi), and `library/<path>/meanings|audio/<id>.json` (one file per source).

### Audio — hands-free pāṭh
- Audio comes **from YouTube** (video id is in the recording's file name as `[videoId]`); the app stores only timings per verse.
- Timings are made by speech recognition of the recording, matched to the book text; extra devotional refrains (e.g. "मंगल भवन अमंगल हारी") are skipped automatically because they match no verse.
- **▶ on every kāṇḍa, every day of each plan, and every verse.** Playing opens the reader, plays the full recording (tune and refrains included), highlights and auto-scrolls to the verse being sung, turns pages by itself, respects the meaning toggles, keeps the screen on — fully hands-free. Manual scrolling pauses auto-follow briefly.
- YouTube's rules: the player must stay visible (≥200×200) while playing — no hidden audio.

### Reader UX (additions)
- **Tapping a kāṇḍa opens it directly** (no intermediate topic list).
- **Continuous scrolling** through a whole kāṇḍa or a day's pāṭh — no Previous/Next page buttons. At the end, one button to the next kāṇḍa / next vishram.
- **Bottom bar = section picker.** Sections listed by name with the **range first, then the topic** (e.g. "Dohā 2–3 · ब्राह्मण-संत-वन्दना"); for plans, a day picker on top. This replaces "Dohā number (0 = …)".
- **Pages follow the book's own sections, not topics**; topic headings appear inside the page.
- **Opening sections** are labelled by verse type and number ("Śloka 1 – Sorathā 4"), never "Dohā 0" or a vague "Invocation".
- **Verse controls never shift centred text:** type label fixed at left of first line; bookmark + ⋮ fixed at right of last line; ▶ at left of last line.
- **Verse numbers** in the verse; Devanagari digits in Hindi mode, Latin in English mode.
- **Light theme by default.**

### Consistency (the owner "loves and admires consistency")
- **Never use different words for the same thing.** One shared label list is used by the menu, Settings, search chips, home buttons, page titles (e.g. "Transliteration", "Recitation mode", "Bookmarks & notes").
- **The same control is the same setting everywhere:** हिं / En / शब्द in the top bar *are* the Settings switches; transliteration and recitation mode are switches in both the ⋮ menu and Settings.
- **One interface language at a time**, following the English-meaning switch (on → English, off → Hindi) — headings, labels, numbers included.

### Pārāyaṇa vidhi pages
- One structured page (no separate Hindi/English versions); the Sanskrit stays, while meanings and explanations follow the selected language.
- Organised as steps: Āvāhana → Pradhāna pūjā (16 offerings list) → Viniyoga → Ācamana & Prāṇāyāma → Karanyāsa → Aṅganyāsa → Dhyāna; each mantra on a card with its "ॐ … नमः" line, its meaning, Hindi names beside English headings.
- **Beginner guidance** boxes (what it means, what to physically do) in both languages; mark them visually distinct from the book's text.
- Word-by-word meaning on tap works for vidhi Sanskrit too (separate Sanskrit glossary for vidhi words).

### Search
- Forgiving transliteration search: final "a" optional (nath = nātha), doubled vowels (puraan), sh/ch/ri/w spellings, nasal n/m optional (jaha/jahan/jahā̐, sant/santa, bhanti). Hindi search ignores anusvara/candrabindu/nukta differences.

### Fonts
- Transliteration needs a font with the combining candrabindu (U+0310): Gentium (subset) as fallback for all Latin text; upright Devanagari font for ॥ in transliteration lines.

### Working style (more)
- **Never leave the owner looking at "processing".** Send a short progress message with what is happening, what's done, and roughly how long the rest takes.
- **Answer "does this use my credits?" plainly:** background computation on the workspace (e.g. speech recognition) doesn't use Claude usage; Claude's own reading/building does.
- **Be honest about machine limits:** the workspace has 2 CPU cores; more parallel workers than cores doesn't speed things up. Background jobs stop after 2 hours and must be resumed.
- **Keep this playbook updated** with every new preference and lesson; it is copied into the project kit.
- **Test on the claude.ai link first** when the owner wants to try something before the GitHub version.

### Learning (Oct 17): YouTube in the claude.ai artifact
- The claude.ai artifact sandbox blocks YouTube frames (both the iframe API script and a plain embed show the broken-page icon). Playback is only possible on the real website (GitHub Pages).
- In the artifact the player waits 5 s; if YouTube hasn't answered, it offers "Listen on YouTube from this verse ↗" (watch?v=ID&t=Ns).
- Plan list rows: a range that spans two kāṇḍas shows one line per kāṇḍa, and the text keeps clear of the ▶ button.

### Preferences (Oct 17, 2026): the repository
- **One repository holds everything**: the website, the scriptures as data, and every script and intermediate file used to make them, so that work can continue if a session is lost. Commit the expensive intermediates (transcripts, extracted text) too.
- **Organization, clarity and consistency come first** because the library will grow (Tulsidas › Rāmacaritamānasa; Ved › Sāmaveda › Upaniṣad › <name> …). Shared code lives in `tools/site` and `tools/audio`; per-work code lives in `tools/works/<work>`. Generated files are never edited by hand. `build.py` validates the library and refuses to build on any inconsistency.
- Adding a meaning source or a reciter is a documented procedure (`docs/HOW-TO.md`), not ad-hoc work.
- **Never show a recording's own title** (uploaded file names, YouTube titles). The player shows the app's own words: the verse ("Bāla-kāṇḍa · Śloka 1") and the reading being played ("30-day · Vishram 1"), followed by the reciter's name.
- Only touch the repositories the owner has created for this; never read other repositories.

### Preferences and lessons (Oct 17, 2026): languages and audio
- **Word meanings must respect the verse's language.** One work can mix languages: the Mānas is Awadhi with Sanskrit ślokas and stutis. Future works bring Marathi (Sai dhūp āratī), Gurmukhi (Japji Sahib), Braj and more. So there is one dictionary per language, each verse carries its language, and lookups follow a declared fallback chain (`docs/LIBRARY.md` §5). The same spelling can mean different things in different languages (या, परे, ते, तौ, करि, हर), so never merge languages into one dictionary.
- **A recitation often runs several half-lines into one breath**, and the speech recogniser returns that as one segment. Giving every verse in the segment the segment's start made a verse begin too early: Bāla 2, "बंदउँ प्रथम महीसुर चरना" began during the previous caupāī. Fix: share the segment among its half-lines by length, and allow up to four half-lines per segment. The alignment rows are cached so timing rules can change without realigning.
- The owner tests audio by checking that each verse starts and ends on its own words. Check boundaries inside long breaths, not only the first verse of a day.
- **Releases must not break phones that have the old version cached.** Moving `gloss.json` to `glossary/` broke a phone that still had the old `app.js` cached; it showed "डेटा नहीं खुल सका". Asset URLs now carry a content hash (`app.js?v=…`), and the service worker revalidates before using its cache. When a data file is renamed or moved, think about readers still running the previous release.
- **Player size (decided Oct 17, 2026):** keep the visible YouTube embed at its 200×200 minimum (YouTube's rule; ~216 pt player). Do not hide the video to play only its sound; it breaks YouTube's terms and could stop working without warning. If the size or the lack of screen-off playback becomes a problem, the agreed alternative is optional local playback of the owner's own downloaded recordings: picked once in Settings, stored on the device, never uploaded.
- **Never push without the smoke test.** On Oct 17 a one-line edit (removing the verse-type sheet) left a dangling `else`, and the live reader would not start for about two minutes. Now `build.py` refuses an `app.js` that doesn't parse, and `tools/site/smoke_test.py` opens every work in a browser before each push.

### Lessons (Oct 17, 2026): a stotra from a video
- **A video's on-screen text can be the source of truth** when the owner says so (Śrī Rāma Rakṣā Stotram: Vande Guru Paramparaam). Screenshots → crop the subtitle band at full width (lines run to the edges) → transcribe line by line into a TSV, keeping the frame number. Repeated screenshots of one line are the same line, not a repeat in the text.
- **When the video's Devanagari and its own transliteration disagree, follow the correct one** (सहस्त्र on screen, sahasra in the transliteration → सहस्र).
- **A website's translation can't be pulled in with the fetch tool** (it won't return a page's full text, and copying a whole translation needs the publisher's permission). Ask the owner for the page as a PDF; its text layer is usable after fixing broken clusters (कं ठ → कंठ, कु ल → कुल).
- **Fix only extraction breaks and plain typos in a publisher's meaning; keep its wording**, even where a clearer phrase comes to mind.
- **Hugging Face may be blocked; GitHub isn't.** sherpa-onnx publishes Whisper ONNX models in its GitHub releases. Its own decoder drops Devanagari (it decodes byte tokens one at a time), so decode the token ids yourself. Whisper gives no timestamps inside a chant, so cut the recording into 4–9 s pieces at its quietest points and transcribe each piece.
- **A work can declare its own verse types** (viniyoga, dhyāna, mantra, colophon) in `work.json` → `types` (name + short tag), instead of adding Mānas-only labels to the app.

### Preferences and lessons (Oct 17, 2026): the Shirdi Dhūpa Āratī
- Each āratī is its own work (shelf: see the decisions below; the āratī is at `hindu/aarti/shirdi-sai/dhoop-aarti`).
- Superseded by the owner's decision below: copy the meanings from the sources the owner gives; write our own (`<lang>-scriptures`) only where none is given.
- When the owner gives two web printouts, use the one they prefer as the base and the other as a second witness. Correct the base only where it is clearly wrong (a missing space, a wrong word, a sense that doesn't fit, broken Sanskrit). Record every correction in the work's `reconciliation.md`.
- Use the Devanagari abbreviation sign ॰ (U+0970) for marks like आ॰ / ध्रु॰. A zero (०) turns into "0" in English mode. Write verse numbers compactly (`।।१।।`) so they never wrap away from the line.
- A work can declare its own verse types (`types` in work.json), so a new kind of text needs no app change.
- Web-page printouts often have a broken Devanagari text layer (pre-base ि and reph out of order, or blank). OCR the page images with Tesseract `mar`/`hin`; `apt-get install tesseract-ocr-mar tesseract-ocr-hin tesseract-ocr-san` works in the workspace, but GitHub's tessdata does not.
- Audio timing needs a Whisper model. If huggingface.co is blocked, use `tools/audio/transcribe_onnx.py`, which takes the model from GitHub.

### Decisions (Oct 17, 2026, late): growing the library
- **Meanings: copy the meanings from the sources the owner gives; write our own only where none is given** (as a separate `<lang>-scriptures` source).
- **The shelf is a REST-like hierarchy, tradition first**: `<tradition>/<genre>/<group…>/<work>`, e.g. `hindu/granth/tulsidas/ramcharitmanas`, `hindu/stotra/rama/ramraksha`, `hindu/aarti/shirdi-sai/dhoop-aarti`, later `hindu/veda/samaveda/upanishad/kena` and `sikh/gurbani/guru-nanak-dev/japji-sahib`. Think about the whole future library when adding a level; reuse levels. A work's id is permanent, while its place on the shelf can change.
- **This is a long-term project**: prefer structure that scales (shared code first, one-entry-per-line shared files, checks in the build) over quick one-off fixes.
- Verse icons sit in the four corners of the verse, in the gutter, so they never touch the text: type tag at top left, bookmark at top right, ▶ at bottom left, ⋮ at bottom right. The verse-type tag is a plain label.
- A single-part work (āratī, stotra) lists its sections straight on its home screen. A work without reading plans shows no plan switch.
- **Every work has "सम्पूर्ण पाठ सुनें / Play the complete work"** on its home screen. It plays from the first recorded verse to the end, across all parts and recordings. Where a stretch has no recording yet, it skips ahead to the next recorded verse and says so.
